# Documentation & Comments Checklist

Review the diff for documentation hygiene at three levels: public API doc comments, in-code comments, and project-level docs.

## Public API Documentation (DocC)

- New `public` / `open` types, methods, properties have a `///` doc comment summarizing purpose.
- Doc comments use DocC syntax where the project already does: `- Parameters:`, `- Returns:`, `- Throws:`, `# Discussion`, symbol links.
- Non-obvious behavior (thread-safety, main-actor expectations, side effects, retry policy, units) is documented.
- Deprecations use `@available(*, deprecated, message: "…", renamed: "…")` with a clear migration path.
- DocC tutorials / catalogs (`.docc`) referenced by the change are updated; broken symbol links are not introduced.

## In-Code Comments

- Comments explain *why*, not *what*; avoid restating the code.
- Tricky algorithms, workarounds, and platform quirks include a brief explanation and a link to the issue, radar, or Apple docs when applicable.
- TODO / FIXME / HACK markers reference an issue number or a date; lone `// TODO` without context is not committed.
- Removed code does not leave behind orphan comments referring to it.
- No autogenerated boilerplate left over (`// Created by …`-style headers are kept consistent with the rest of the project — keep them all or remove them all, do not mix).

## Tests As Documentation

- New test names describe the behavior under test, not the implementation detail.
- Non-obvious test setup (fixture choice, time freezing, simulator state) has a short comment.
- `// Given / // When / // Then` comments are used only if the rest of the test suite uses them.

## Project-Level Documentation

- README, CHANGELOG, ADRs, or onboarding docs are updated when the change affects:
  - Public API of a shared module
  - Build / run / test instructions
  - Required environment variables, entitlements, or capabilities
  - Supported OS versions or device classes
- Release-notes or "What's New" entries are queued for user-visible changes (App Store metadata, changelog file, etc.) when the project tracks them.
- Architecture decisions that change long-standing conventions are captured in an ADR or design-doc when the project keeps one.

## Localization Notes

- New `LocalizedStringResource` / `String(localized:)` calls include a `comment:` for translators when context is non-obvious.
- String catalog entries with placeholders or pluralization are documented for translators.

## Red Flags To Always Surface

- New `public` API with no doc comment in a project that otherwise documents public API.
- TODO without owner, issue, or date.
- Comment that contradicts the code (stale comment after a refactor).
- Behavior change that affects build/run instructions but leaves README untouched.
- Removed feature whose docs still claim it exists.
